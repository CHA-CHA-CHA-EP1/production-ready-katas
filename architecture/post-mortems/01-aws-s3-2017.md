## Incident Summary

ในวันที่ 28 กุมภาพันธ์ 2017 S3 ใน us-east-1 ไม่สามารถ serve request ได้เป็นเวลาหลายชั่วโมง

เหตุการณ์เริ่มจาก engineer ที่ทำการ debug billing system ได้ run command เพื่อลด capacity ของ S3 subsystem หนึ่ง แต่ input ที่ระบุในคำสั่งนั้นผิดพลาด ทำให้ server จำนวนมากกว่าที่ตั้งใจถูก remove ออกจาก system server เหล่านั้นเป็นส่วนหนึ่งของ 2 S3 subsystems หลัก ได้แก่ index subsystem (ที่ track metadata ของ object ทุกชิ้น) และ placement subsystem (ที่ตัดสินใจว่า data จะไปอยู่ที่ไหน) เมื่อ server ถูกลบออกไปมากเกินไป subsystem เหล่านี้ต้อง restart ใหม่ทั้งหมด

การ restart ใช้เวลานานกว่าที่ AWS คาดไว้มาก เนื่องจาก subsystem ต้องสร้าง in-memory state ใหม่จาก data จำนวนมากที่สะสมมาหลายปี ระหว่างที่ restart อยู่นั้น S3 ใน us-east-1 ไม่สามารถรับ request ได้

ผลกระทบลุกลามกว้างกว่าที่คาด เพราะ service จำนวนมากภายใน AWS เองก็พึ่งพา S3 รวมถึง AWS Service Health Dashboard ซึ่งก็ใช้ S3 host static assets เช่นกัน ทำให้ dashboard ไม่สามารถ update status ให้ลูกค้าทราบได้ในช่วงที่ outage รุนแรงที่สุด นอกจากนี้ service อื่นๆ ใน us-east-1 ที่พึ่งพา S3 ก็พัง cascade ตาม

## Design Review Questions — ก่อน incident ควรถามอะไร

หากคุณเป็น architect ที่กำลัง review S3 หรือ service ที่ใช้ S3 ก่อนเหตุการณ์นี้ คำถามอะไรจะ surface risk นี้ได้?

<details>
<summary>แนวคิดหลังจากคิดเองแล้ว</summary>

**เรื่อง capacity change safety:**
- "runbook สำหรับ capacity removal มีการ validate input ก่อน execute ไหม? มี dry-run mode ไหม?"
- "command นี้ reversible ไหม? ถ้า reverse ต้องใช้เวลานานแค่ไหน?"
- "blast radius ของ command นี้ถ้า input ผิดคืออะไร? มี limit ป้องกัน accidental large-scale change ไหม?"

**เรื่อง recovery time:**
- "ถ้า subsystem ต้อง full restart ใช้เวลานานแค่ไหน? เคยวัดไหม? ขนาด data มีผลต่อ restart time ไหม?"
- "warm-up time ของ in-memory state มี estimate ไหม? scale กับขนาด dataset ยังไง?"

**เรื่อง monitoring coupling:**
- "status page ของ service X ขึ้นอยู่กับ service X เองไหม? ถ้าใช่ — เมื่อ service ล่มจะแจ้งลูกค้าได้ยังไง?"
- "มี out-of-band communication channel ถ้า primary status page ไม่ available ไหม?"

**เรื่อง cascade dependency:**
- "service ไหนบ้างที่พึ่งพา S3 ใน critical path? ถ้า S3 down จะมีผลอะไรต่อ service เหล่านั้น?"
- "dependency เหล่านั้น graceful degrade ได้ไหม หรือจะ fail hard?"

## Design Changes That Would Have Limited the Blast Radius

ลองคิดเองก่อนว่าจะออกแบบ system ยังไงให้ลด impact ได้ แล้วค่อยดูแนวคิดด้านล่าง

<details>
<summary>แนวคิดหลังจากคิดเองแล้ว</summary>

**1. Operation safety gate บน capacity change**
- ใส่ confirmation step หรือ limit จำนวน server ที่ remove ได้ใน single command
- บังคับ dry-run output ก่อน execute จริง
- บันทึก audit trail ทุก capacity change command พร้อม actor

**2. Subsystem isolation ระหว่าง restart**
- ออกแบบให้ restart ของ subsystem หนึ่งไม่กระทบ subsystem อื่น (bulkhead pattern)
- มี read-only fallback mode ในช่วง partial availability

**3. Status page decoupling**
- Host status page บน infrastructure ที่แยกจาก service ที่ monitor
- ใช้ static hosting บน CDN ที่ independent จาก S3 us-east-1
- มี pre-baked static page สำหรับ "we are aware of an issue" ที่ serve ได้แม้ primary infra ล่ม

**4. Multi-region dependency awareness**
- Map ว่า service ไหนใช้ S3 ใน critical path
- สำหรับ service ที่ critical — มี fallback ถ้า S3 unavailable (cache, retry with backoff, graceful degradation)

</details>

## Key Themes

- **Runbook safety:** command ที่มี large blast radius ควรมี guard ป้องกัน accidental wrong input
- **Recovery time ที่ไม่รู้จริง:** ระยะเวลา restart ของ subsystem ใหญ่ไม่ได้ถูก test ที่ scale จริง
- **Monitoring ที่พึ่งพา service ที่ตัวเองดู:** anti-pattern ที่ทำให้ communication ล้มเหลวในช่วง worst moment
- **Cascade dependency:** shared service ที่ relied on โดย service หลายตัวในเวลาเดียวกัน สร้าง correlated failure
